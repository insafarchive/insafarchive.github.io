## 1. Why GitHub-Based Governance?

Insaf Archive is intentionally engineered as an open, verifiable, static public-interest archive deployed via GitHub Pages. It deliberately avoids dynamic backends, administrative databases, and server-side secret tokens.

This architectural decision enforces transparency:
- **No Invisible Edits:** Every addition, correction, or status transition exists as an immutable commit in git history.
- **Peer Review by Default:** Changes proposed in the browser-local Editorial Studio cannot modify the public archive until vetted by authorized repository maintainers through a GitHub Pull Request.
- **Zero Token Exposure:** No personal access tokens, GitHub API credentials, or database passwords exist in client-side JavaScript.

## 4. Submitting Proposals via GitHub

### Option A: Submitting via GitHub Issue (Non-Developer Contributors)
1. In the Studio's **Export & GitHub PR** tab, click **Copy Issue Text**.
2. Click **Open GitHub Issues** to navigate to the repository's issue creation portal.
3. Select the *Archival Record Submission* or *Correction Request* template.
4. Paste the copied markdown text (which includes the embedded JSON payload).
5. Submit the issue. Repository maintainers will convert the issue payload into a branch.

### Option B: Submitting via GitHub Pull Request (Technical Contributors)
1. Fork the `insafarchive/insafarchive` repository.
2. In the Studio, click **Download .json File** to obtain the compiled payload.
3. Apply the proposed record objects to:
   - `src/data/dossiers/dossiersData.ts` (for dossiers, claims, sources, media)
   - `src/data/dossiers/dossierAudits.ts` (for claim audit entries)
4. Run the four local validation gates:
   ```bash
   npm run test
   npm run validate-data
   npm run typecheck
   npm run build
   ```
5. Open a Pull Request against the `main` branch.
6. In the PR description, paste the **Pull Request Checklist** generated by the Studio.

## 5. Maintainer Review Checklist (PR Verification Gates)

Before merging any editorial Pull Request, repository maintainers must confirm:

- [ ] **Bilingual Equivalence:** English and Urdu texts describe the same substantive facts; no unreviewed machine translation.
- [ ] **Source Provenance:** All cited source IDs exist and represent genuine sovereign instruments or corroborated reports. No invented URLs.
- [ ] **Epistemological Distinction:** Allegations, official defenses, and police positions are strictly categorized and not conflated with judicial findings.
- [ ] **Sub Judice Compliance:** If the case is non-concluded (`ongoing`, `stayed`, `pending_appeal`), a prominent pending proceedings notice is attached.
- [ ] **Privacy & Redaction:** Private bystanders, witnesses, and juvenile records are completely redacted (`piiRedacted: true`).
- [ ] **Automated CI Success:** The GitHub Actions continuous integration workflow (`.github/workflows/ci.yml`) passes 100% of tests.
